# ADR-0003: Change-Detection Granularity and Storage

Status: Proposed (pending Design Review / Gate G2)
Date: 2026-09-24

## Context

FR-010 requires regeneration when a source change affects FR-006-extracted
information (modules, classes, functions, signatures, parameters, docstrings).
FR-011 requires that a change limited to implementation-body content that does
*not* alter that extracted information must **not** cause a rewrite. NFR-002 asks
the system to avoid "obviously unnecessary repeated work." This requires both a unit
of comparison (what is hashed/compared) and a place to persist prior state between
CLI runs (the CLI is stateless between invocations per FR-001's manual-invocation
model).

## Options Considered

**A. Comparison unit:**
1. Hash the raw file content (whole `.py` file bytes/text).
2. Hash a canonical serialization of the *extracted documentation model*
   (module/class/function names, signatures, parameter lists, decorators, return
   annotations, docstrings) — explicitly excluding function/method body statements.
3. Use filesystem modification time (`mtime`) as a proxy for "changed."

**B. Storage location for prior-state data:**
1. A sidecar manifest file alongside the generated output (e.g.,
   `docs/generated/.docsync-manifest.json`).
2. A hidden per-project directory outside `docs/generated/` (e.g.,
   `.docsync/cache.json` at the repo root).
3. Embed the prior-state hash directly inside the generated Markdown file itself,
   as an HTML comment in a fixed header block.

## Decision

- **Comparison unit:** Option A2 — hash a canonical serialization of the
  *extracted documentation model per source file*, explicitly excluding function
  and method body statements.
- **Storage:** Option B3 — embed the resulting hash (and a short "generated by"
  banner) as an HTML comment at the top of the generated Markdown output itself,
  rather than a separate manifest file.

## Rationale

- **FR-011 correctness (option A2 vs A1/A3):** Hashing raw file content (A1) or
  using `mtime` (A3) cannot distinguish a body-only edit from a signature/docstring
  edit — both change the file's bytes and timestamp equally, which would fail
  FR-011 outright (AC-005). Hashing only the FR-006-extracted model, with body
  statements deliberately excluded from the serialization before hashing, is the
  only option of the three that can satisfy both FR-010 (AC-004) and FR-011
  (AC-005) simultaneously.
- **NFR-002 (avoid unnecessary work):** comparing the new per-file model hash
  against the previously stored hash lets the pipeline skip re-rendering and
  re-writing output when nothing FR-006-relevant changed, without needing to
  re-read or diff the previous Markdown text.
- **FR-009 (never touch files outside the generated-output location) and storage
  choice:** Requirements authorize the tool to write only under `docs/generated/`
  (FR-008) or a user-configured output location (FR-016) — there is no requirement
  authorizing a second, separate state directory elsewhere in the repository.
  Embedding the hash inside the one generated file the tool already owns avoids
  introducing an additional, unauthorized write location and keeps FR-009's
  "designated generated-output location" singular and easy to reason about.
  This also means the change-detection state travels with the output file itself
  (e.g., if a developer copies or commits the generated file, its own change
  fingerprint travels with it), rather than depending on a second file being kept
  in sync.

## Trade-offs Accepted

- The embedded-hash approach couples change-detection state to the output file's
  survival: if a human manually deletes or edits the generated file's header
  comment, the next run cannot compare against prior state and will regenerate
  (safe default — worst case is one unnecessary rewrite, not a missed required
  update).
- A separate manifest file (B1) would allow tracking multiple output files/state
  independently of output content, but v1's scope (FR-008's single
  `docs/generated/code-documentation.md`-style output) does not need that
  generality; this can be revisited if a future version splits output across many
  files.
- This decision is hard to reverse once the manifest format ships, because
  changing the comparison unit or storage location invalidates all previously
  generated files' change-detection state (a one-time forced full regeneration
  would be required on upgrade).

## Consequences

- The Markdown Renderer must emit a stable, machine-parseable header comment
  (banner + hash) at a fixed location in the generated file.
- The Change Detector component reads that header back on the next run before
  deciding whether to regenerate.

## Resolution (2026-09-24, remediation update — resolves design-review DR-005)

This ADR's original Decision/Consequences described the *comparison unit* (Option
A2: per-source-file model hash) precisely, but described the *storage* (Option B3:
embedded header comment) only as holding "the resulting hash" — a single value —
while `docs/architecture.md` Section 12's own prose already required tracking a
*set* of per-file hashes (to detect additions, deletions, and per-file changes
independently). `docs/design-review.md` DR-005 correctly identified this as an
unspecified "comparison unit vs. storage format" gap: a single aggregate hash and a
per-file hash table are both plausible readings of the original text, and they are
not equivalent designs.

**Clarification (not a reversal of the A2/B3 decision above):** storage is a
**per-file hash table**, not a single aggregate hash, embedded as a single-line JSON
object inside the existing header-comment banner, keyed by each file's path relative
to the configured source root, e.g.:

```
<!-- docsync:v1 sha256={"pkg/a.py": "3f2a...", "pkg/sub/b.py": "9c11..."} -->
```

Keys are serialized in sorted order for determinism (consistent with this
architecture's requirement that rendering be pure/deterministic, `docs/architecture.md`
Section 10). This is the same Option B3 (embed in the generated file's own header)
already decided above — only the internal shape of what is embedded is now made
concrete, per `docs/architecture.md` Section 12.
